# Card 轮询优化讨论

## 当前实现分析

### 1. 轮询频率：60秒

**当前行为**：
- 每 60 秒全量重新创建所有 cards
- 无论数据是否变化，都会执行

**问题**：
- ⚠️ **频率可能过高**：对于生产环境，60秒可能太频繁
- ⚠️ **资源浪费**：即使没有变化，也会执行全量删除和重建

### 2. 全量重建策略

**当前实现**：
```go
func (c *CardCreator) CreateCardsForUnit(tenantID, unitID string) error {
    // 1. 删除该 unit 下的所有旧卡片
    c.repo.DeleteCardsByUnit(tenantID, unitID)
    
    // 2. 重新创建所有卡片
    // 即使卡片内容没有变化，也会删除重建
}
```

**问题**：
- ❌ **多余操作**：如果数据没有变化，删除和重建是浪费的
- ❌ **性能开销**：每次都要执行 DELETE + INSERT
- ❌ **数据丢失风险**：删除和创建之间有时间窗口（虽然很短）
- ❌ **card_id 变化**：每次重建都会生成新的 card_id，可能导致前端缓存失效

## 优化方案讨论

### 方案 A：增加轮询间隔（简单，推荐）

**方案**：
- 将轮询间隔从 60 秒增加到 **5-10 分钟**（300-600 秒）
- 保持全量重建策略不变

**优点**：
- ✅ 实现简单，只需修改配置
- ✅ 减少数据库压力
- ✅ 减少不必要的删除重建操作

**缺点**：
- ❌ 仍然会在没有变化时执行全量重建
- ❌ 数据变化后最多延迟 5-10 分钟才能反映

**建议配置**：
```bash
export CARD_POLLING_INTERVAL="300"  # 5 分钟（推荐）
# 或
export CARD_POLLING_INTERVAL="600"  # 10 分钟（更保守）
```

**适用场景**：
- 数据变化不频繁的环境
- 对实时性要求不高的场景
- 快速优化方案

---

### 方案 B：增量更新（复杂，但最优）

**方案**：
- 比较现有 cards 和期望 cards
- 只创建新 cards
- 只更新变化的 cards（使用 UPDATE 而不是 DELETE+INSERT）
- 只删除不再需要的 cards

**实现思路**：
```go
func (c *CardCreator) UpdateCardsForUnit(tenantID, unitID string) error {
    // 1. 获取当前数据库中的卡片
    existingCards := c.repo.GetCardsByUnit(tenantID, unitID)
    
    // 2. 计算应该存在的卡片（基于当前数据）
    expectedCards := c.calculateExpectedCards(tenantID, unitID)
    
    // 3. 比较差异
    toCreate, toUpdate, toDelete := c.diffCards(existingCards, expectedCards)
    
    // 4. 只更新变化的卡片
    for _, card := range toCreate {
        c.repo.CreateCard(...)
    }
    for _, card := range toUpdate {
        c.repo.UpdateCard(...)  // 使用 UPDATE 而不是 DELETE+INSERT
    }
    for _, card := range toDelete {
        c.repo.DeleteCard(card.CardID)
    }
}
```

**优点**：
- ✅ **性能最优**：只更新变化的 cards
- ✅ **数据安全**：保留未变化的 cards，减少数据丢失风险
- ✅ **card_id 稳定**：未变化的 cards 保持相同的 card_id
- ✅ **可追踪**：可以记录哪些 cards 被更新了

**缺点**：
- ❌ **实现复杂**：需要比较逻辑、处理并发更新等
- ❌ **开发工作量大**：需要实现 `GetCardsByUnit`、`UpdateCard`、`diffCards` 等方法
- ❌ **测试复杂**：需要测试各种边界情况

**需要实现的功能**：
1. `GetCardsByUnit(tenantID, unitID)` - 获取现有 cards
2. `UpdateCard(cardID, ...)` - 更新 card（而不是删除重建）
3. `diffCards(existing, expected)` - 比较差异逻辑
4. Card 比较逻辑（比较 devices、residents、card_name 等字段）

**适用场景**：
- 数据变化频繁的环境
- 对性能要求高的场景
- 长期优化方案

---

### 方案 C：混合方案（推荐）

**方案**：
- **短期**：采用方案 A（增加轮询间隔到 5-10 分钟）
- **长期**：实现方案 B（增量更新）

**优点**：
- ✅ 快速见效：先解决频率问题
- ✅ 长期优化：逐步实现增量更新
- ✅ 风险可控：分阶段实施

## 性能影响分析

### 当前实现（60秒全量重建）

假设：
- 10 个 units
- 每个 unit 平均 2 个 cards
- 每次重建：DELETE 20 条 + INSERT 20 条

**每小时操作量**：
- 轮询次数：3600 / 60 = 60 次
- DELETE 操作：60 × 20 = 1200 次
- INSERT 操作：60 × 20 = 1200 次
- **总计：2400 次数据库操作/小时**

### 方案 A（300秒全量重建）

**每小时操作量**：
- 轮询次数：3600 / 300 = 12 次
- DELETE 操作：12 × 20 = 240 次
- INSERT 操作：12 × 20 = 240 次
- **总计：480 次数据库操作/小时**
- **减少：80% 的操作量**

### 方案 B（增量更新，假设 10% 变化率）

**每小时操作量**：
- 轮询次数：60 次（保持 60 秒）
- UPDATE 操作：60 × 2 = 120 次（假设每次只有 2 个 cards 变化）
- CREATE 操作：60 × 0.2 = 12 次（假设偶尔新增）
- DELETE 操作：60 × 0.1 = 6 次（假设偶尔删除）
- **总计：138 次数据库操作/小时**
- **减少：94% 的操作量**

## 建议

### 短期建议（立即实施）

1. **增加轮询间隔到 5 分钟（300秒）**
   - 实现简单，只需修改配置
   - 减少 80% 的数据库操作
   - 对实时性影响可接受（最多延迟 5 分钟）

2. **保留启动时立即执行**
   - 服务启动时立即执行一次全量创建
   - 确保服务重启后 cards 及时生成

### 长期建议（后续优化）

1. **实现增量更新**
   - 比较现有 cards 和期望 cards
   - 只更新变化的 cards
   - 可以保持 60 秒轮询间隔，但操作量大幅减少

2. **考虑事件驱动模式**
   - 当设备/住户绑定关系变化时立即触发
   - 结合定时任务（每天一次全量更新）作为保底
