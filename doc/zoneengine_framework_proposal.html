zoneengine 框架重整提案

当前 23 文件 + wiring 子目录 10 文件（共 33 个），没有明确层次。先定责任边界，再决定文件分组。

① 一句话定义

zoneengine = 物理空间占用 FSM。
输入 SignalEvidence（多源融合证据）→ 内部 (Vacant/Leaving/Occupied) 三态状态机 → 输出 ZoneEvent（翻转沿事件）。

④ 唯一的真正问题：stream_publisher.go 644 行做了 7 件事

当前 stream_publisher.go 责任清单

#内容所属责任
1StreamPublisher struct + AggregatorPuller interface装配
2Setters: SetRoomDedup / SetAggregator / SetIdentity装配
3OnZoneEvent + handleRoomZoneEvent (ZoneEventListener 实现)Builder 入口
4applyRoomDedupInPlace + republishRoomAfterBed (radar+sleepad fusion)Dedup
5applyAloneAndRisk (Alone/Standing/Risk 派生 + state-change-anchored ts)Builder 主逻辑
6cacheLastRoom/Bed + SnapshotRoomStates/BedStates (cache 管理 + 给 zonealarm)Cache
7Run + tickRepublishStates + tickPullAndPublish (60s)Tick
8RefreshRoomRiskAndMaybePublish (5s zonealarm Tick 调)Builder 重算
9PublishRoomState/BedState/TargetState/BedSleepStage (Redis write)Publish

"东一个西一个" 主要在这里：RoomState 的派生 + 重算逻辑散在 #3 / #5 / #8 三处，每处都要记得 fillStanding+applyAloneAndRisk 顺序，容易遗漏（我刚刚改的时候就漏了一次）。

⑤ 提案：拆 stream_publisher.go 为 4 个文件

新文件责任从原文件抽出预估 LOC
publisher.go StreamPublisher struct + setter + 3 Publish API + envelope marshal 原 #1, #2, #9 ~180
room_state_builder.go RoomState 唯一构建/重算入口：BuildFromEvent(e) / RefreshFromCache(cidr, now)
内部依次调 Translator / Dedup / fillStanding / applyAloneAndRisk		 原 #3, #4, #5, #8 ~250
state_cache.go lastRoomState/lastBedState/roomKindByCIDR + cache mutators + Snapshot APIs 原 #6 ~110
publisher_tick.go Run(ctx) + tickRepublishStates + tickPullAndPublish (60s 主循环) 原 #7 ~80

关键收益：

  • RoomState 的"诞生 / 重算"只在 room_state_builder.go 一个文件 — 唯一入口，无散点
  • publisher.go 变薄，只管 envelope + redis write
  • state_cache.go 给 zonealarm Snapshot 用的接口独立成单元（可测）
  • 5s Refresh vs 60s tick 关系清楚（都通过 RoomStateBuilder 入口）
