# Radar 事件系统分析

## 一、两套事件系统概述

Radar 设备协议文档中存在**两套事件系统**，它们服务于不同的目的和使用场景：

### 系统1：设备直接上报事件（3.5节）

**命令格式**：`cmd: "event"`  
**主题**：`/prefix/event/productId/UID/post`  
**类型字段**：`type`（数值：1, 2, 3）

| type | 事件类型 | data 格式 | 说明 |
|------|---------|-----------|------|
| 1 | 进出事件 | 数组，包含 `track-id`, `event`, `area_type` | 进入/离开房间/区域/床等 |
| 2 | 姿态变化事件 | 数组，包含 `track-id`, `pose` | 跌倒、坐地、床上坐起等姿态变化 |
| 3 | 人数变化事件 | 对象，包含 `number-people` | 检测到的人数变化 |

**特点**：
- 格式简单，只有3种基础事件类型
- 适合持续订阅实时数据时使用（通过 monitor 数据也可以获得相同信息）
- 数据粒度较粗，需要进一步处理才能获得告警

### 系统2：第三方平台事件通知（2.3节）

**命令格式**：`cmd: "DEVICE_EVENT"`  
**主题**：可能通过 HTTP/HTTPS 接口推送（文档第2节）  
**类型字段**：`event`（字符串："1"到"10"）

| event | 事件类型 | 事件级别 | params 参数 | 说明 |
|-------|---------|---------|-------------|------|
| "1" | 人数变化 | 普通事件 | `count`（人数） | - |
| "2" | 跌倒事件 | 告警 | 无 | 设备检测出跌倒 |
| "3" | 呼吸心率相关事件 | 告警/普通事件 | `breath`, `heartbeat`, `alarmType` (11-16) | 11-呼吸过高, 12-呼吸过低, 13-呼吸暂停, 14-心率过高, 15-心率过低, 16-生命体征弱（告警） |
| "4" | 进出门事件 | 普通事件 | `entry2Exit` (0-进入, 1-离开) | - |
| "5" | 上线/离线事件 | 普通事件 | `isOnline` (0-在线, 1-离线) | - |
| "6" | 进出床事件 | 普通事件 | `entry2Exit` (0-进入, 1-离开) | - |
| "7" | 信号差事件 | 普通事件 | `recovery` (0-触发, 1-恢复) | - |
| "8" | 倾角异常事件 | 普通事件 | `recovery` (0-触发, 1-恢复) | - |
| "9" | 其他告警 | 告警 | `alarmType` (1-10) | 1-离床未归, 2-滞留, 3-长时间无人活动, 4-坐地告警, 5-床上坐起告警, 6-10未开放 |
| "10" | 进出告警区域 | 普通事件 | `entry2Exit` (0-进入, 1-离开) | - |

**特点**：
- 事件类型更细化（10种）
- **已包含告警判断**（区分普通事件和告警）
- 包含更多设备状态信息（上线/离线、信号差、倾角异常等）
- 参数结构更丰富（每种事件有特定的 params）
- 部分告警需要设备配置开关才会触发

## 二、两套系统的关系和映射

### 2.1 事件类型的对应关系

| 系统1 (cmd: "event") | 系统2 (cmd: "DEVICE_EVENT") | 说明 |
|---------------------|----------------------------|------|
| type=3 (人数变化) | event="1" | 人数变化事件 |
| type=2 (姿态变化, pose=5跌倒) | event="2" | 跌倒告警 |
| type=2 (姿态变化, pose=2/5/7/8/10/11) | event="9" (alarmType=4/5) | 坐地告警、床上坐起告警 |
| type=1 (进出事件, event=1/2进出门) | event="4" | 进出门事件 |
| type=1 (进出事件, event=5/6进出床) | event="6" | 进出床事件 |
| type=1 (进出事件, event=3/4进入区域) | event="10" | 进出告警区域 |
| - | event="3" | 呼吸心率异常（系统1中没有，从 monitor/stat 数据计算） |
| - | event="5" | 上线/离线（系统1中没有） |
| - | event="7" | 信号差（系统1中没有） |
| - | event="8" | 倾角异常（系统1中没有） |
| - | event="9" (alarmType=1/2/3) | 离床未归、滞留、长时间无人活动（系统1中没有，需计算） |

### 2.2 使用场景区别

**系统1（cmd: "event"）**：
- 适用于**持续订阅实时数据**的平台
- 通过 `/prefix/event/productId/UID/post` MQTT 主题接收
- 数据格式简单，需要平台自行处理和计算告警
- 已集成到 `wisefido-radar` 服务中（topic_type: "event"）

**系统2（cmd: "DEVICE_EVENT"）**：
- 适用于**按需订阅**或通过**HTTP推送**的平台
- 可能是通过 HTTP/HTTPS 接口推送给第三方平台
- 事件已细化和分类（包含告警判断）
- 包含设备状态事件（上线/离线、信号差等）
- **目前代码中可能未处理此格式**

## 三、与我们当前实现的关系

### 3.1 当前实现

当前 `wisefido-radar` 服务处理的是**系统1**（cmd: "event"）：
- 主题：`/prefix/event/productId/UID/post`
- 格式：`{cmd: "event", type: 1/2/3, data: ...}`
- 输出到 Redis Stream：`iot:event:stream`

### 3.2 系统2的处理

系统2（cmd: "DEVICE_EVENT"）：
- **格式不同**：使用 `event` 字符串字段（"1"到"10"），而非 `type` 数值字段
- **参数结构不同**：每种事件有特定的 `params` 参数
- **包含更多信息**：设备状态、告警级别等
- **可能需要额外的处理逻辑**

## 四、建议

1. **确认需求**：需要处理系统2（DEVICE_EVENT）的事件吗？
2. **如果不需要**：当前系统1已满足需求，可以继续使用
3. **如果需要**：需要：
   - 识别 `cmd: "DEVICE_EVENT"` 的消息
   - 解析 `event` 字段（字符串"1"到"10"）
   - 处理不同的 `params` 参数结构
   - 映射到现有的 Redis Stream 格式或创建新的格式

## 五、关键差异总结

| 维度 | 系统1 (cmd: "event") | 系统2 (cmd: "DEVICE_EVENT") |
|------|---------------------|----------------------------|
| **命令字段** | `cmd: "event"` | `cmd: "DEVICE_EVENT"` |
| **类型字段** | `type` (int: 1, 2, 3) | `event` (string: "1"到"10") |
| **事件数量** | 3种基础类型 | 10种细化类型 |
| **告警判断** | 无（需平台计算） | 有（区分普通事件/告警） |
| **设备状态** | 无 | 有（上线/离线、信号差、倾角异常） |
| **参数结构** | 简单（data数组/对象） | 复杂（每种事件有特定params） |
| **使用场景** | MQTT持续订阅 | HTTP推送或按需订阅 |
| **当前处理** | ✅ 已实现 | ❌ 未实现 |
