# Radar 设备 HTTPS 认证和 MQTT 协议文档

> **重要**: 关于设备与 Server 之间所有字段的转换规则，请参考 [Radar_Field_Conversion_Table.md](./Radar_Field_Conversion_Table.md)。该文档详细列出了所有字段的原始值、转换后值、转换公式、取值范围等信息，避免遗漏单位转换错误。

## 2.2. 了解设备工作流程

设备运行按上述阶段执行：

1. **启动阶段**：设备执行内部初始化，包括雷达模组初始化、wifi 连接/4G 连接。不管 wifi/4G 是否连接成功，都会往下执行下一个阶段。

2. **HTTPS 认证阶段**：设备向认证服务器请求认证，获得 MQTT 服务账号授权。
   - (1) 如果成功，则到下一个阶段；
   - (2) 如果因为网络原因或服务器返回失败等，会间隔 5 秒后重试；
   - (3) 如果 10 分钟都无法认证完成，将会执行重启

3. **MQTT 连接阶段**：设备连接 MQTT 服务器。
   - (1) 如果成功，则进入正常使用阶段。
   - (2) 如果失败，则重试；
   - (3) 如果连续 10 分钟都无法连接到网络，将会执行重启

4. **正常使用阶段**：可通过 MQTT 对设备进行设置属性/获取设备轨迹等
   - (1) 如果网络掉线，会重新进入 MQTT 连接阶段
   - (2) 网络掉线期间，设备无法设置属性，除告警主题内容外，数据都会丢失

## 3. 设备协议对接

### 3.1. 通信协议及格式

设备与平台采用 MQTT 通信协议，MQTT 协议版本：MQTT 3.1.1，支持加密。

### 3.2. HTTPS 认证

HTTPS 认证目的是检查设备是否合法，如果合法则可获得设备连接 MQTT 服务的账号信息。

- HTTPS 认证在设备启动 8 秒后进行（前 8 秒是等待 Wi-Fi 就绪以及雷达属性读取），认证一旦认证通过，后续除非设备重启，否则不再进行第二次认证。
- 认证时携带设备版本/MAC 等不可变属性，后续 get 属性时不再上报这些属性

HTTPS URL 地址（POS 形式）:
https://服务器地址:服务器端口号/prod-api/thirdmqtt/v2/auth/device

## HTTPS 认证消息格式

### 请求消息

```json
{
  "uid": "xxxxxxxxxxx",
  "type": 1,
  "auth": "xxxxxxxxx",
  "salt": "12345",
  "MCU": {
    "hw": "2.0",
    "sw": "Oct 23 2024 09:20:18",
    "mac": "xxxx",
    "iccid": " "
  },
  "Radar": {
    "hw": "2.3",
    "sw": "Dec 4 2024 08:53:22",
    "cap": 15
  }
}
```

### 请求字段说明

| 属性 | 类型 | 必填 | 说明 |
|------|------|------|------|
| uid | String | Y | 设备序列号 |
| type | Number | Y | 设备类型 |
| auth | Obj | Y | 认证随机数，服务器可忽略 |
| salt | String | Y | 认证随机数，服务器可忽略 |
| MCU | Obj | Y | 主控信息 |
| MCU.hw | String | - | 主控硬件类型
- 4G 设备: 1.0, 1.1
- Wi-Fi 设备: HC2-2.0, TK2-2.3 |
| MCU.sw | String | - | 主控固件编译日期 |
| MCU.mac | String | - | Wi-Fi 设备属性 |
| MCU.iccid | String | - | 4G 设备属性 |
| Radar | Obj | Y | 雷达信息 |
| Radar.hw | String | - | 雷达硬件类型
- T 型号: 1.0
- S 型号: 2.3 |
| Radar.sw | String | - | 雷达固件编译日期 |
| Radar.cap | String | - | 雷达功能类别 |

## HTTPS 回应消息格式

### 响应消息

```json
{
  "msg": "操作成功",
  "code": 200,
  "data": {
    "uid": "xxxxxxxxxx",
    "mqtt": {
      "clientId": "xxx",
      "timeout": 30,
      "keepalive": 60,
      "server": "xxx",
      "port": 1056,
      "account": "xxxx",
      "pwd": "xxxxx",
      "protocol": "xxxxx",
      "prefix": "xxxxx",
      "productId": "4"
    }
  }
}
```

### 响应字段说明

| 字段名 | 类型 | 说明 |
|--------|------|------|
| msg | String | 操作结果的描述信息，此处为 "操作成功"，用于直观告知请求方操作状态 |
| code | Integer | 状态码，200 表示请求操作成功 |
| data | Object | 包含具体业务数据的对象，此处为与 MQTT 相关的配置等数据 |
| data.uid | String | 设备的唯一标识字符串 |
| data.mqtt | Object | 包含 MQTT 连接相关配置的对象 |
| data.mqtt.clientId | String | MQTT 客户端的唯一标识，用于 MQTT 连接时区分不同客户端 |
| data.mqtt.timeout | Integer | MQTT 连接等操作的超时时间，单位通常为秒 |
| data.mqtt.keepalive | Integer | MQTT 心跳包发送间隔时间，单位为秒，用于保持连接活性，默认为 60 秒 |
| data.mqtt.server | String | MQTT 服务器的地址，客户端通过该地址连接 MQTT 服务 |
| data.mqtt.port | Integer | MQTT 服务器的端口号，客户端通过该端口连接 MQTT 服务 |
| data.mqtt.account | String | 连接 MQTT 服务的账号，用于身份认证 |
| data.mqtt.pwd | String | 连接 MQTT 服务的密码，与账号配合进行身份认证 |
| data.mqtt.protocol | String | 表示是否采用 MQTTS 加密协议
- 1：不加密
- 2：加密 |
| data.mqtt.prefix | String | MQTT 发布消息时主题的前缀，用于规范主题格式等，详见 3.3.2/3.3.3 |
| data.mqtt.productId | String | 自定义产品 id，范围为 0-255，详见 3.3.2/3.3.3 |

## 3.3. MQTT 建立连接

### 3.3.1. MQTT 连接处理

通过 HTTPS 获取具体连接信息配置 MQTT，并订阅相关主题

**连接成功处理**：
- 如果 MQTT 连接成功，等待 5 秒后，关闭蓝牙

**连接失败或断联处理**：
根据如下规则决定是否打开蓝牙：
1. **非 PoE 版本**：断联后打开蓝牙
2. **POE 版本**：
   - 如果配置了静态 IP 则不打开
   - 否则打开蓝牙

### 3.3.2. 设备订阅主题

设备订阅的主题为如下 3 个：

**说明**：
- `prefix` 和 `productId` 由 HTTPS 认证时返回
- `UID` 为产品序列号，在产品背面有相应标签
- `prefix` 等同于主题命名空间，方便与平台已有的主题进行区隔
- 如果 `prefix` 是空字符串，则不需要携带 `prefix`
- `productId` 是 0-255 任意数字，方便平台按某种分组或类别来管理设备

| 设备订阅主题 | 作用 |
|------------|------|
| `/prefix/prop/productId/UID/get` | 设置/读取设备属性，详见 3.4 节 |
| `/prefix/monitor/productId/UID/get` | 订阅设备实时数据，详见 3.7.1 |
| `/prefix/func/productId/UID/get` | 调用雷达功能：重启、打电话等，详见 3.8 节 |

### 3.3.3. 设备发布主题

设备发布的主题为如下 6 个：

**说明**：
- `prefix` 和 `productId` 由 HTTPS 认证时返回
- `UID` 为产品序列号，在产品背面有相应标签
- `prefix` 等同于主题命名空间，方便与平台已有的主题进行区隔
- 如果 `prefix` 是空字符串，则不需要携带 `prefix`
- `productId` 是任意数字，方便平台按某种分组或类别来管理设备

| 设备发布主题 | 作用 |
|------------|------|
| `/prefix/prop/productId/UID/post` | 返回设置/读取设备属性的结果，详见 3.4 节 |
| `/prefix/monitor/productId/UID/post` | 发布设备订阅的实时数据，详见 3.7 |
| `/prefix/func/productId/UID/post` | 返回功能调用结果，详见 3.8/3.9 节 |
| `/prefix/stat/productId/UID/post` | 上报轨迹/睡眠统计数据，详见 3.6 节 |
| `/prefix/event/productId/UID/post` | 上报事件/日志，详见 3.5 节 |
| `/prefix/alarm/productId/UID/post` | 上报告警，详见 3.5 节 |

### 属性设置、获取和返回的主题定义

#### 设置属性

**主题**：`/prefix/prop/productId/UID/get`

**消息格式**：
```json
{
  "cmd": "update",
  "requestId": "sadibaiubd123",
  "data": {
    "key1": "value1",
    "key2": "value2"
  }
}
```

**说明**：可下发 1 到多个 key 和 value 值

#### 读取属性

**主题**：`/prefix/prop/productId/UID/get`

**消息格式**：
```json
{
  "cmd": "read",
  "requestId": "sadibaiubd123",
  "data": {
    "key": ["key1", "key2", "key3"]
  }
}
```

**说明**：
- 可读取 1 到多个 key 的值
- 如果没有携带 key，则返回所有的属性 key value

#### 属性返回

**主题**：`/prefix/prop/productId/UID/post`

**消息格式**：
```json
{
  "cmd": "read/update",
  "code": 200,
  "requestId": "sadibaiubd123",
  "data": {
    "key1": "value1",
    "key2": "value2"
  }
}
```

**说明**：
- 在设置属性和获取属性时，返回 1 到多个 key 和 value 值
- `code` 表示是否有错误
- 注：`requestId` 为平台下发配对数，保证下发数据包返回同样 `requestId`

### 雷达属性关键注意点

- 如果涉及雷达高度和边界内容更改，需等待 5 秒后，参考 3.8.1 内容重启雷达。
- 如果涉及安装方式（顶装/侧装）切换，设备会清除所有区域设置，并将边界恢复为默认值

**建议属性的下发顺序**：
1. 工作模式
2. 跌倒和呼吸心率参数设置
3. 安装方式
4. 安装高度
5. 边界和区域
6. 最后等待 5 秒重启雷达

### 3.4.1. 基本属性

设备的基本属性包括工作模式、安装方式和安装高度，属性通过 key-value 方式进行下发，其定义如下：

| 属性 | Key | Value |
|------|-----|-------|
| 工作模式 | `radar_func_ctrl` | 3：人数轨迹
7：跌倒检测
11：呼吸睡眠
15：全功能（床位监护） |
| 安装方式 | `radar_install_style` | 0：顶装
1：侧装

**注意**：TK2 设备仅支持顶装，请勿设置为侧装
安装方式切换后，由于坐标系发生变化，设备会清除所有区域设置，并将边界恢复为默认值。因此安装方式应在边界和区域配置前设定。 |
| 安装高度 | `radar_install_height` | 单位为分米，取值范围：15-33
- 顶装默认值：28
- 侧装默认值：15

**注意**：高度变更后应等待 5 秒后重启雷达 |

### 3.4.2. 检测边界

雷达通过 4 个顶点坐标标识的矩形来表示检测边界，设置检测边界时需按 `{x1,y1,x2,y2,x3,y3,x4,y4}`。

**不同设备的顶点坐标排列方法**：
- 第一行左图为 HC2 设备顶装时的坐标排列。注意设备背部朝上，俯视方式进行观察
- 第一行右图为 HC2 设备侧装时的坐标排列，注意设备挂墙上进行观察
- 第二行图为 TK2 设备顶装时的坐标排列，注意设备背部朝上，俯视方式进行观察

**1-2-3-4 顶点顺序下发坐标**

| 属性 | Key | Value |
|------|-----|-------|
| 检测边界 | `rectangle` | 将 1-2-3-4 个顶点按坐标按如下格式顺序发到雷达：
`{x1, y1; x2, y2, x3, y3, x4, y4}`
其中坐标数值单位为分米

**设置举例**：
- 顶装检测边界为 X 轴±3 米，Y 轴±2 米，则传输格式为：
  `{-30, -20; 30, -20; -30, 20; 30, 20}`
- 侧装检测边界为 X 轴±3 米，Y 轴 0-4 米，则传输格式为：
  `{-30, 0; 30, 0; -30, 40; 30, 40}` |

### 3.4.3. 区域属性

设备可支持最大 16 个区域的设置，区域类型包括：

| Area-type 值 | 区域类型 | 作用 |
|-------------|---------|------|
| 0 | 无效 | 表示此区域未使用，将当前有效的区域类型设置为 0 等同于删除区域 |
| 1 | 自定义区域 | 装饰使用，雷达不对此区域进行处理 |
| 2 | 床 | 进入离开此区域会产生进床离床事件
**注**：如果床的中心点在雷达下方，系统会自动将其类型更改为 5 |
| 3 | 干扰区域 | 此区域运动物体会被屏蔽，可用于去除马桶冲水、风扇等影响 |
| 4 | 门 | 在门附近形成/消失的目标会产生进房/离房事件 |
| 5 | 监护床 | 在监护床范围的人员可进行呼吸心率测量及睡眠报告分析 |

**设置区域的 key-value 属性定义**：

| 属性 | Key | Value |
|------|-----|-------|
| 设置区域 | `declare_area` | 传输格式：`{area-id, area-type, x1, y1; x2, y2, x3, y3, x4, y4}`

- `area-id` 表示需要设置的区域 id，取值范围 0-15
- `area-type` 表示区域类型，取值范围 0-4。当床区域的中心点坐标在雷达正下方（X=0，Y=0 附近）时，系统自动将区域类型从 2（普通床）更改为 5（监护床）。设置为 0 等同于将此区域进行删除
- 后续 8 个值代表区域的 4 个顶点坐标，其顺序与 3.4.2 定义相同

**注**：此接口一次只能设置一个区域 |

### 3.4.4. 跌倒参数

设备支持设置跌倒参数，其 key-value 值如下：

| 属性 | Key | Value |
|------|-----|-------|
| 跌倒参数 | `fall_param` | 此属性为 202404 以及后续的新固件使用，支持更多功能配置：
16 字节数组，按 BASE64 进行编码为字符串。各个字节的定义如下：

- **字节 0-2 和 6-15**：保留未使用
- **字节 3**：跌倒告警时间，单位为 10 秒，默认值为 6（代表 60 秒），设置范围 0-250
- **字节 4**：功能开关
  - bit0 设置为 1：打开坐地告警
  - bit1 设置为 1：打开姿态检测
  - bit2 设置为 1：打开床上坐起告警
  - **注意**：bit 0 和 bit2 设置为 1 时，设备会自动将 bit 1 设置为 1
  - **注意**：Bit2 设置需要 202501 以上版本固件才支持
- **字节 5**：坐地告警时间，单位为 10 秒，默认值为 10（代表 100 秒），设置范围 1-250 |

### 3.4.5. 呼吸心率参数

设备支持设置呼吸心率参数，其 key-value 值如下：

**注意**：呼吸高阈值不能低于呼吸低阈值，心率高阈值不能低于心率低阈值

| 属性 | Key | Value |
|------|-----|-------|
| 呼吸心率参数 | `heart_breath_param` | 16 字节数组，按 BASE64 进行编码为字符串。各个字节的定义如下：


-**字节 0**：呼吸高阈值，单位为次/分钟，默认值为 24，设置范围[10, 100]

- **字节 1**：心率高阈值，单位为次/分钟，默认值为 90，设置范围[10, 255]

- **字节 2**：呼吸低阈值，单位为次/分钟，默认值为 8，设置范围[1, 20]

- **字节 3**：心率低阈值，单位为次/分钟，默认值为 50，设置范围[1, 100]

- 当呼吸/心率超过高低阈值时，将会产生异常事件

- **字节 4**：持续检测。默认为 0，设置为 1 时将不依赖轨迹不间断进行呼吸心率测量

- **字节 5**：生命体征弱检测时间阈值。单位为分钟，默认值 10，可设置范围[1-15]

- **字节 6**：生命体征弱检测灵敏度。默认值为 5，可设置范围[1, 99]。值越大越容易触发生命体征弱告警

- **注**：4/5/6 字节内容需 202404 版本固件支持

- **字节 7-15**：预留字段 |

### 3.4.6. 角度校准

HC2 设备内置加速度传感器，正常情况下，设备在出厂时已经做好角度校准。

如发现设备角度与实际偏差较大，可在设备水平放置在地面/桌面/天花板时，进行角度校准。校准后设备将以校准时状态作为水平 0°。

| 属性 | Key | Value | 备注 |
|------|-----|-------|------|
| 水平校准 | `run_Horizontal` | - | HC2 设备支持，TK2 不支持 |

### 3.4.7. 设置结束铃声

HC2 内置的通话结束铃声是中文语音，有些地区可能需要本地区的提示语音，可以通过以下方式来定制铃声。

| 属性 | Key | Value | 备注 |
|------|-----|-------|------|
| 结束铃声 | `voice_end_tip` | 格式为"文件长度:铃声的 URL" | HC2 设备支持，TK2 不支持
- 铃声文件不大于 150KB，格式要求为 mp3

## 3.6. 统计数据上报

雷达每分钟会进行一次轨迹数据统计和睡眠数据统计，统计结果会进行上报，平台可基于统计数据进行处理分析。

**重要**：平台应将每分钟的统计结果进行存档，按天维度进行分析。此数据如丢失，设备上无法恢复。

**主题**：`/prefix/stat/productId/UID/post`

**格式**：
```json
{
  "cmd": "sleep_trajectory",
  "data": {
    "sleep": "xxxxxx",
    "track": "xxxxxx"
  }
}
```

### sleep 字段说明

`sleep` 字段为 base64 编码的定长 16 字节的数组。在有人进入监护床时，分钟级呼吸睡眠数据以 1 分钟 1 次的频率进行上报；否则不进行数据上报。报文长度固定为 16 字节，其定义如下：

| 字节 | 属性名称 | 定义 |
|------|---------|------|
| 0 | 标识符 | 固定为 0xff，表示为睡眠统计 |
| 1 | 实时呼吸值 | 单位：次/分钟 |
| 2 | 实时心率值 | 单位：次/分钟 |
| 3-4 | 睡眠统计信息 | 睡眠算法未公开，本字段信息不公开 |
| 5 | 分钟级平均呼吸 | 单位：次/分钟 |
| 6 | 分钟级平均心率 | 单位：次/分钟 |
| 7-12 | 睡眠统计信息 | 睡眠算法未公开，本字段信息不公开 |
| 13 | 呼吸心率事件 | 过去一分钟出现的状态/事件
- bit 1 & bit 0 代表过去 1 分钟的呼吸状态:
  - 00: 呼吸正常
  - 01: 呼吸过低
  - 10: 呼吸过高
  - 11: 呼吸暂停
- bit 3 & bit 2：代表过去 1 分钟的心率状态
  - 00: 心率正常
  - 01: 心率过低
  - 10: 心率过高
  - 11: 未定义
- bit 5 & bit 4：代表生命体征情况
  - 00: 状态正常
  - 01: 未定义
  - 02: 未定义
  - 11: 生命体征弱
- bit 7 & bit 6：代表过去 1 分钟的睡眠状态
  - 00：未定义
  - 01：浅睡
  - 10：深睡
  - 11：清醒 |
| 14-15 | 睡眠统计信息 | 睡眠算法未公开，本字段信息不公开 |

**注意**：
- 呼吸心率事件基于 3.4.5 设置的呼吸心率参数，经设备算法处理后生成
- 除生命体征弱异常外，一般不建议基于分钟级的呼吸心率事件立刻产生报警

**当前睡眠算法不对外公开**，如需获得完整睡眠报告，需按如下方法执行：
- 根据 3.5 的内容或 3.7.1 的事件通知，记录保存每一个进出监护床的事件和对应时间点
- 根据 3.3 的 MQTT 连接流程自行记录设备上线下线事件和对应时间点
- 记录和保存本节所的睡眠统计数据及对应时间点
- 调用 HTTPS 接口，将上述进出监护床事件+上下线事件+睡眠统计数据 发送到清澜服务器，由其计算睡眠报告进行返回。HTTPS 接口定义参见 4.1 和 4.2 节

### track 字段说明

`track` 字段为一分钟一次的轨迹统计数据，平台可基于此数据统计用户静坐、步行等信息。上报的报文格式如下：

`track` 为 base64 编码的定长 16 字节的数组。16 字节定义如下：

| 字节 | 属性名称 | 定义 |
|------|---------|------|
| 0 | 版本标识符 | 当前取值 1 或 2 |
| 1 | 人数 | 当前上报时刻雷达检测到的人数。取值 0-8 |
| 2~3 | 行走距离 | 过去一分钟统计的行走距离，单位为米
取值范围 0-32767，采用 Big-Endian 字节序填写
**注意**：在多人情况下不做统计 |
| 4 | 行走时长 | 过去一分钟统计的行走时间，单位为秒
**注意**：在多人情况下不做统计 |
| 5 | 静坐时长 | 未开放使用 |
| 6 | 躺卧时长 | 过去一分钟统计的静止时间，单位为秒
**注意**：在多人情况下不做统计 |
| 7 | 站立时长 | 过去一分钟统计的静止时间，单位为秒
**注意**：在多人情况下不做统计 |
| 8 | 多人时长 | 过去一分钟统计的有多人存在的时间，单位为秒
这段时间将不做行走距离、行走时长、静止时长等统计 |
| 9~15 | rsv | 未开放使用 |

## 3.7. 实时数据订阅和上报

### 3.7.1. 实时数据订阅

为了减少设备流量消耗，实时性的轨迹和呼吸心率数据缺省不上报，如需要获取，需要服务器向设备订阅。订阅消息需要指定订阅有效期（最大 3600 秒，即 1 个小时，建议默认使用 1 分钟），超过有效期需要重新订阅才能持续获得数据。

**注意**：多次订阅时，以最后一次订阅的有效期为准。

**订阅主题**：`/prefix/monitor/productId/UID/get`

**格式**：
```json
{
  "cmd": "subscription",
  "data": {
    "content": 0,
    "duration": 30
  }
}
```

**参数说明**：
- `content`：0-同时订阅，1-订阅轨迹，2-订阅呼吸心率
- `duration`：订阅时长，最大 3600 秒，即 1 个小时

### 3.7.2. 实时数据上报

订阅成功后，实时轨迹数据上报的主题：`/prefix/monitor/productId/UID/post`

**格式**：
```json
{
  "cmd": "subscription",
  "data": {
    "track": "xxxxxxxxx",
    "bh": "xxxxxxxxx"
  }
}
```

### track 字段说明

`track` 为 base64 编码的 16 字节*N 长度的字节数组，N 为雷达设备侦测到的人数。

- 在有人状态时，轨迹数据以 1 秒 1 次的频率进行上报
- 在无人状态时，轨迹数据以 30 秒 1 次频率上报，目标 ID 固定为 88

在有人状态下，每 16 字节代表 1 个人，其定义如下：

| 字节 | 属性名称 | 定义 |
|------|---------|------|
| 0 | 目标 ID | 有人状态时，数值取值 0-7，代表人员编号
无人状态时，数值固定为 88，表示无人 |
| 1~3 | 轨迹坐标 | 1-3 字节分别为 x/y/z 坐标
- x 和 y 坐标单位为分米，取值范围-127~127
- z 坐标单位为厘米，取值范围 0-255 |
| 4-11 | 预留字段 | 预留调试使用 |
| 12 | 剩余时间 | 单位为秒，取值 0-60，仅在自动测量边界时使用 |
| 13 | 人员姿态 | 0: 初始化
1: 行走
2: 疑似跌倒
3: 蹲坐
4: 站立
5：跌倒确认
6: 卧床
7: 疑似坐地
8: 确认坐地
9: 普通床上坐起
10: 疑似床上坐起
11: 确认床上坐起

**注意**：
- 3、6 姿态需配置打开"姿态显示"功能，需升级到 202406 版本固件才支持
- 7、8 姿态需配置打开坐地告警开关，需升级到 202407 以上版本固件才支持
- 9-11 姿态需配置打开床上坐起开关，需升级到 202501 以上版本固件才支持 |
| 14 | 人员事件 | 0：无事件
1：进入房间
2：离开房间
3：进入区域
4：离开区域

**注意**：如设备上报了不在上述事件定义值的事件可忽略 |
| 15 | 区域 ID | 在 14 字节内容为 3 或 4 时，此字段标识人员进出的区域 ID |

### bh 字段说明

`bh` 为 base64 编码的定长 16 字节的数组。

- 在有人进入监护床时，秒级呼吸心率数据以 2 秒 1 次的频率进行上报
- 否则不进行数据上报

呼吸心率报文长度固定为 16 字节，其定义如下：

| 字节 | 属性名称 | 定义 |
|------|---------|------|
| 0 | 标识符 | 固定为 0，表示实时呼吸心率 |
| 1 | 呼吸值 | 单位：次/分钟 |
| 2 | 心率值 | 单位：次/分钟 |
| 3-12 | 预留 | 预留调试使用 |
| 13 | 状态事件 | bit 7 & bit 6：代表过去 1 分钟的睡眠状态
- 00：未定义
- 01：浅睡
- 10：深睡
- 11：清醒 |
| 14 | 稳定度 | **注**：此值需要在 202501 版本固件后才能使用，否则应忽略
bit 1 & 0：表示过去 10 秒钟是否有动作干扰测量
- 00：未定义
- 01：有较大动作
- 10：有较小动作
- 11：无干扰 |

### 3.8.2. 自动测量边界

雷达支持自动测量边界功能，功能描述参考 2.1 节说明书。

自动测量功能通过 3.4.2 节描述的设置检测边界属性实现，其过程如下：

1. **用户点击开始**：服务器将检测边界的坐标值全部设置为-127 并下发设备，启动测量
2. **用户绕行房间一圈**：进行边界测量。在此过程中，如需获得人员轨迹进行实时显示，请参考 3.7 进行实时轨迹数据订阅
3. **用户点击结束**：服务器将检测边界的坐标值全部设置为 127 并下发设备，结束测量
4. **平台获取设备属性**：提取设备测量到的边界数值

**注意**：设备收到启动测量后，有 60 秒倒计时，如果 60 秒后收不到结束测量指令，将会自动结束测量并将边界恢复到设备默认值。设备倒计时数据可通过 3.7.1 的实时轨迹报文第 12 字节获得。



### 3.8.4. OTA 流程

#### 3.8.4.1. 获取 OTA 固件

清澜科技会定期发布可升级固件，可联系清澜技术支持获取。

清澜提供的固件信息如下，除最后两个外，其余信息需要通过 OTA 消息推送给设备：
- ESPFileSize：主控固件的大小，不超过 2M
- ESPFileSHA256：主控固件的 sha256 校验值
- RadarFileSize：雷达固件大小，单位字节，最大不超过 500K
- RadarFileSHA256：雷达板固件的 sha256 校验值

清澜技术提供的 URL 一般为中国大陆服务器文件。如果设备无法连接到清澜服务器的 URL 下载固件，则需要开发者自行提供 HTTP 文件服务器放置固件，上述 URL 需更改为正确的 URL。注意：通信固件一般超过 512KB，自行提供的文件服务器需要支持指定 Range 下载，Range 下载返回码应使用 206 而不是传统的 200.

| 序号 | 字段名称 | 定义 |
|------|---------|------|
| 1 | espsfver | 主控版本。升级前建议与 3.4 节获得的 sfver 属性进行对比，确保一致 |
| 2 | ESPFileUrl | 主控固件的 URL，最大长度 250 字节，要求为 https 或 http 协议

**注意**：通信固件一般超过 512KB，文件服务器需要支持指定 Range 下载，Range 下载返回码应使用 206 而不是传统的 200 |
| 3 | ESPFileSize | 主控固件的大小，不超过 2M |
| 4 | ESPFileSHA256 | 主控固件的 sha256 校验值 |
| 5 | radarsfver | 雷达板版本，升级前建议与 3.4 节获得的 radarsfver 属性进行对比，确保一致 |
| 6 | RadarFileUrl | 雷达板固件的 URL，最大长度 250 字节，要求为 https 或 http 协议 |
| 7 | RadarFileSize | 雷达固件大小，单位字节，最大不超过 500K |
| 8 | RadarFileSHA256 | 雷达板固件的 sha256 校验值 |
| 9 | app_compile_time | 主控固件编译时间 |
| 10 | radar_compile_time | 雷达固件编译时间 |

#### 3.8.4.2. OTA 升级流程

OTA 流程如下图所示，服务器使用 OTA 主题推送固件信息给设备。设备将执行如下流程：
- 从文件服务器下载雷达固件，进行 sha256 的校验以及版本校验后升级
- 从文件服务器下载主控固件，进行 sha256 的校验以及版本校验后升级
- 在升级过程中，如步骤成功或失败，通过进度消息反馈情况
- 升级成功后将自动重启
- 配件升级由主控设备下发 OTA 参数，并进行以上相同步骤升级

**OTA 请求主题**：`/prefix/func/productID/UID/get`

**OTA 请求格式**：
```json
{
  "cmd": "ota",
  "requestId": "1F3F0.1793753537",
  "data": {
    "espfileUrl": "https://test.bin",
    "espfilesha256": "ndiuqaniudnaiudnasiund122",
    "espfilesize": 123,
    "espver": "2.0",
    "radarfileUrl": "https://test.bin",
    "radarfilesha256": "ndiuqaniudnaiudnasiund122",
    "radarfilesize": 123,
    "radarver": "2.0"
  }
}
```

**设备 OTA 回应主题**：`/prefix/func/productID/UID/post`

**格式**：
```json
{
  "cmd": "ota_return",
  "data": {
    "uid": "09AF08F17823",
    "progress": 25,
    "errMsg": ""
  }
}
```

**参数说明**：
- `progress`：进度值
  - 10：雷达固件下载完成
  - 25：雷达固件升级完成
  - 56：主控固件下载完成
  - 100：全部固件升级完成
  - -1：升级失败，具体原因可查看 errMsg 提示

OTA 成功完成后，检查是否真正 OTA 成功方法：
- 设备重启上线后，等待一分钟左右，使用 3.4 节方法获取设备属性
- 设备属性中的 `radar_compile_time` 和 `app_compile_time` 属性，是否跟 3.8.4.1 表格提供的内容一致。如果一致，则认为成功，否则可能是升级失败或 3.8.4.1 提供的信息有误。
如 OTA 失败，请按如下步骤检查修复：
- 检查设备是否上电在线
- 检查 OTA 参数是否正确
- 检查文件服务器是否可正常下载
- 如 OTA 依然失败，请联系清澜技术销售人员进行处理
